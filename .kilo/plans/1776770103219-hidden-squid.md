# Plan: Handling 100 Concurrent Users on Vercel Free Plan

## Goal
Analyze the graphicdesign-app codebase for performance bottlenecks and propose optimizations to handle 100 concurrent users on Vercel's Hobby (free) plan, which offers 1 million function invocations, 4 CPU-hours, 360 GB-hrs memory, and concurrency up to 30,000.

## Current Architecture Summary
- **App Type**: Next.js full-stack with Supabase (DB/storage), Gemini AI for image generation.
- **User Flow**: Users submit generation forms, enqueuing jobs asynchronously. Background API processes jobs (prompt merging, image gen via Gemini, upload to Supabase).
- **Key Bottlenecks**:
  - AI calls (Gemini): High latency (1-3s per job), rate limits, image processing (base64 conversion).
  - DB queries: Potential slowdowns without proper indexing on growing tables (generations, users).
  - File handling: Uploads/downloads for large images.
  - Concurrency: Job queue prevents blocking, but DB locks possible under high load.
- **Vercel Limits**: Hobby allows 1M invocations/month, auto-scaling to 30K concurrency. Free for included usage; exceedance incurs costs.

## Feasibility Assessment
- **Usage Pattern**: Burst of 100 users submitting generations simultaneously, each taking ~90 seconds.
- **Concurrency Handling**: Asynchronous queue decouples UI, but parallel processing 100 jobs would overload resources (e.g., memory: 100 jobs * ~2GB * 90s >> 360 GB-hrs limit). Implement throttling to limit active jobs (e.g., 5-10 concurrent).
- **Limits Impact**: 100 bursts/day could use ~200-500 invocations. Bandwidth: assuming 5MB/image, 100 images = 500MB, within 100GB but monitor for multiple generations/user.
- **Bottlenecks to Address**: High per-job time (90s), resource usage during bursts; optimize AI calls, reduce image sizes, add throttling.

## Proposed Optimizations
1. **Code Optimizations**:
   - Reduce Gemini calls: Cache merged prompts or brand analyses. Implement LRU cache for frequent prompts.
   - Image Compression: Resize/compress uploaded images before base64 to reduce memory usage (target <1MB per image) and bandwidth.
   - Error Handling: Implement exponential backoff for rate limits; avoid retries that exceed 300s duration.
   - DB Indexing: Add indexes on `generations.user_id`, `generation_jobs.status`, `brands.user_id` for faster queries.
   - Throttling: Limit concurrent job processing (e.g., max 5-10 active jobs) to prevent resource overload during bursts.

2. **Architecture Improvements**:
   - Caching Layer: Use Supabase edge functions or Redis (if available) for prompt/brand context caching.
   - Load Balancing: Ensure job processing is distributed; use Vercel regions if needed.
   - Monitoring: Add logging for job durations, errors; monitor CPU/memory via Vercel dashboard.

3. **User Experience Enhancements**:
   - Progress Updates: Optimize polling (increase intervals) to reduce client requests.
   - Limits Awareness: Add UI warnings for credit depletion or high load.

## Implementation Steps
1. **Audit Current Performance**:
   - Run load tests (simulate 100 concurrent submissions) using tools like Artillery or k6.
   - Profile function durations via Vercel logs.

2. **Implement Optimizations**:
   - Update `lib/gemini.ts` and `lib/merge-prompt.ts` for caching and compression.
   - Modify job processing in `app/api/process-job/route.ts` to implement concurrency throttling (check active jobs before claiming).
   - Add DB migrations for indexes via Supabase CLI.
   - Test changes locally with Next.js dev server.

3. **Monitor and Scale**:
   - Deploy to Vercel Hobby; monitor usage via dashboard.
   - If limits approached, consider Pro plan upgrade or cost optimizations.

## Risks and Tradeoffs
- **Cost**: Hobby is free for included usage; optimizations reduce overages.
- **Complexity**: Caching and throttling add code complexity; ensure cache invalidation and proper queue management.
- **User Experience**: Throttling may increase wait times during bursts, but prevents failures.
- **Fallback**: If still overloaded, upgrade to Pro plan or add user-level rate limiting.
